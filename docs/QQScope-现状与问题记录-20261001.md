## 一、这是个什么项目

一句话：**把自己 QQ 里的聊天记录读出来，在本地做统计和情绪分析，用来看自己最近的状态。**

说全一点，它是给我自己用的自我观察工具。不是给人看病的东西，也不是什么情绪测评 App，所有文案都得写清楚「辅助自我观察，非医疗诊断」。最早做它的起因很简单：想知道自己这半年到底在什么时候话最多、跟谁聊得最凶、是不是又在熬夜。QQ 的聊天记录其实是最真实的样本，但它藏在客户端里，翻起来基本没戏。

数据怎么进来的，分成两条路，互相不干扰：

**窗口 A，走本地数据库（离线、存量）。** 电脑上 QQ 自己的 `nt_msg.db` 用的是 SQLCipher 加密，还带 1024 字节的头。流程是：用 QQBackup 那个密钥提取脚本把 key 抠出来，剥头、解密、解析 protobuf，最后落到自己的库里。这条路能拿到很久以前的历史，主号 1605289411 目前是 28 万多条。坑主要在两处，一是密钥跟着 QQ 版本走，QQ 一升级 key 就变；二是联系人昵称、群名这些在另外几个库（`profile_info.db`、`group_info.db`）里，密钥跟主库不一样，早期一直没搞定，后来换思路直接找新密钥才通。

**窗口 B，走机器人框架（在线、增量）。** 用 NapCat 的 Windows 无头一键版，跟本机平时用的 QQ 完全独立——不启动它、不关它、不往里注入，这点是硬要求。NapCat 登录后监听 OneBot HTTP（3000 端口），我们拉好友、群、历史消息，另外还挂了个实时采集线程，把新到的消息持续灌进库，不用重启框架。

库、界面、产出是这么分的：

- 主库按账号分开存，`data/accounts/<QQ>/qqscope.db`（早期是单库，见第二节）
- Web 端是 FastAPI + 一个单文件前端，跑在 15555；页面有总览、会话、导出、动态、数据源、AI 解读、设置
- 导出支持 HTML / TXT / MD，可以每人一个文件也可以合并，带 zip；HTML 是自包含的，没有外部请求
- 媒体那块做了语音转文字（本地 faster-whisper）、图片、文件、表情、名片卡
- 另外有便携包（免装 Python）和一个单文件 exe

几条一直在守的底线：数据全在本机，任何时候不上传；要调 AI 之前先把要发出去的内容预览给我看；界面上不能出现外部 CDN、远程字体、远程图片。

## 二、今天遇到并处理掉的问题

### 1. 前后端通信

这个是最后查出来的，也是最有意思的一个。

现象是网页用起来一直"不利索"，请求偶尔要等很久。我最开始怀疑是代理——这台机器上挂着 `127.0.0.1:7890` 的系统代理，之前本地请求就被它劫持过（Python 那边得加 `trust_env=False` 才正常）。但查了注册表，绕过列表里本来就有 `localhost` 和 `127.*`，代理不背这个锅。

实测才发现是监听地址的问题：

```
http://127.0.0.1:15555   -> 200 (202 ms)
http://localhost:15555   -> 200 (2090 ms)   ← 慢了一个数量级
http://[::1]:15555       -> 连接被拒绝
```

后端一直绑的是 `0.0.0.0`，也就是只有 IPv4。浏览器打开 `localhost` 的时候会先试 IPv6 的 `::1`，被拒之后才回退到 IPv4，**每次请求白白等两秒**。页面上的轮询是密着的（登录门 3 秒一次，还有实时采集、框架日志），两秒的回退乘上去，用起来就是"网页和后台通信有问题"。

修的过程里我自己先踩了一个坑：想当然把监听改成 `host="::"`，结果这台机器上它变成 v6-only，反倒把 `127.0.0.1` 彻底断了（实测连接被拒）。改成 IPv4 主服务不动、额外用守护线程挂一个 `::1` 的回环监听，两边才都正常：

```
127.0.0.1 -> 177 ms（冷启动）
localhost ->  55 ms   （原来 2090 ms）
[::1]     ->  43 ms   （原来直接拒绝）
```

顺带记两个也属于"通信"的旧账，都是今天之前踩过、现在已修的：一是验收脚本 `verify.py` 明明 9/9 全绿却退出码是 1，原因是最后那行 `print("全绿 ✅")` 在 GBK 控制台抛了编码异常；二是 `build_web.py` 直接往 stdout 打中文，被别人当子进程读的时候会乱码。还有 `server/app.py` 从来没挂载 `/assets`，这个放到第 4 小节讲。

目前还留着一条慢的：`/api/framework/status` 每次要 1.1 秒左右，它要查 WMI 进程列表和 netstat。只在框架终端页用到，不影响主流程，加个两秒缓存就能好，但今天没动。

### 2. 文件存储

原来的问题是**所有账号的数据挤在一块儿**：一个 `data/qqscope.db` 装着所有 QQ 的联系人、消息、动态，`media_cache`、`avatars`、`export` 也都是全局唯一一份。查询逻辑上早就按 `account_qq` 过滤了，前端也是分开的，但物理上就是混着的，这既不符合"每个号自己的东西单独放"的要求，也让人不放心。

现在的样子：

```
data/
  accounts/
    1605289411/
      qqscope.db          本体
      media_cache/        这个号的图片语音缓存
      avatars/            这个号看到的头像
      export/             这个号的导出产物
      decrypt/  pack/     解密和解析过程中的中间文件
    1438830763/
      qqscope.db
      avatars/  export/  ...
  accounts.db             账号注册表（谁在、有多少条）
  server/  framework/     全局配置和框架日志
```

`core/store.py` 的 `connect()` 现在接受账号参数，传账号就打开那个号的库，不传就是注册表；删账号从"删一堆行"变成了"删整个目录"。真实库已经迁完了，拆出两个账号目录（主号 283048 条 / key 8 条），迁移前备份在 `data/backup/legacy_split_20261001_224741.db`，老的单库没删、改名成 `data/qqscope.db.migrated` 留着。文件那一层也做了迁移，备份在 `data/backup/files_split_20261001_225944/`。

迁移脚本的原则是**判不出归属的一律不删也不乱移**，所以现在还留在原地没动的有：老的导出目录里 52 个没有 `_meta` 记录的旧任务（加起来 17708 个文件，是最大的一坨）、212 个头像、28 个媒体缓存、26 个解密中间文件、2 个 pack 文件。这些都是历史遗留产物，不影响新数据——新产生的文件都直接落到对应账号的文件夹里。

还有一处没收尾：`pack` 的写盘点在 `server/onebot.py` 和 `server/reader.py` 里，这次没在改动范围内，所以 `data/pack` 下还剩两个根目录的文件。

### 3. 网页端的预览

这块要分开说，因为"预览"在项目里指好几个地方。

**AI 解读的预览**今天之前是坏的，而且是彻底坏的那种：页面上一直显示「等待数据加载…」。原因很蠢——调用 `ensureReport()` 的地方从第四个版本就在，但函数的定义在某次改版里被删掉了，页面上直接抛 `ensureReport is not defined`，后面的渲染全断。修完之后的实测是：AI 页 `data-js-errors=0`，预览里有真实内容（能看到账号昵称和消息总数）。这个预览本身是有意义的，因为按约定要调 AI 之前，得先把将发出去的内容摆出来给人看一眼。

**媒体的预览**包括图片灯箱、语音气泡、文件卡片、名片卡和表情。这里的老大难是群聊里的历史图片——QQ 客户端自己清了缓存，本地就没有原文件，命中率一直上不去。解决办法是用 NapCat 的登录态回去把缺失的媒体拉回来（`nc_get_rkey` + pack 里已有的 fileid 拼直链），界面上有补下载入口，限速 0.6 秒一条、可以中断。语音那边走过弯路：本地 ASR 一开始慢得离谱（35 分钟只跑完 198 条），后来发现是线程超订（10 个 worker 每个开 8 线程去挤 20 核），改成多进程少线程才正常；现在语音的 pending 已经清到 0。

**导出页**那块的"预览"是指时间段筛选和分组：能选全部时间 / 最近 7 天 / 最近 30 天 / 自定义起止，会话列表按私聊在前、群聊在后分组，全选私聊、全选群聊这些快捷键也都有。

需要坦白一句：我最开始并不知道你说的"网页端预览"具体指哪一处。上面这三块是代码里所有叫预览的地方，我按今天核过的情况都写了。如果指的是别的现象（比如消息列表滚动的懒加载、资料卡弹出、或者导出 HTML 打开后的样子），那还得再看一次，我这次先把已知的落下来，不乱猜。

### 4. 3D 旋转背景

背景这个需求是从"界面太素了，跑个模型环绕一下"来的。做法是本地 three.js + GLTFLoader 加载一个 VRM 模型（kei，43 MB），在登录页和主界面上做环绕动画。素材是本地文件，不放 CDN，静态 HTML 里也不写 `<script src>`，都是运行时按需注入的，打不开就退化成一层 CSS 光晕。

今天查出来一个挺典型的 bug：**后端从来没挂载过 `/assets`**。也就是说，这个 3D 背景在真实产品里一直没生效——请求 `/assets/vendor/kei.vrm` 直接 404，前端静默降级成 CSS 光晕，界面上看不出错，只是模型不出来。之所以一直没发现，是因为 v10 的验收用的是测试脚手架 `web/selftest/v10_server.mjs`，那个脚本自己实现了 `/assets` 的转发，所以"自测全绿、真机不生效"。这个教训值得记一笔：**素材类的断言，必须在真后端上再跑一遍，不能只信自建的 mock 服务。**

补上挂载之后实测是 `200 / 44,845,856 B`，模型能正常加载。素材目录缺失时不挂载、前端降级，其它功能不受影响——这是有意的，因为那个 VRM 有 43 MB。

围绕这个文件还有几件事要说明白：

- 它**不进 git**（43 MB 纯二进制，放仓库里不合适），`.gitignore` 里排掉了 `web/assets/`，换机器要跑 `scripts/fetch_assets.ps1` 从参考项目复制过来
- 便携包和 exe 里**是打进去的**，所以那个 exe 有 145 MB，其中很大一块就是这个模型
- 无头浏览器（SwiftShader 软渲染）里帧率很低，代码里做了自适应：帧率连续低于 24 就自动关掉 3D，属于设计内的降级，不是 bug
- 连接页默认开、主界面默认关，设置页里有开关，偏好存在 localStorage

## 三、还没解决 / 需要确认的

按重要性排：

1. **便携包没做过异机实测。** 换目录跑通过，但在另一台没装 Python、没装 QQ 的电脑上首次启动，还没真正试过。
2. **老导出的归属问题。** 上面说的 17708 个旧文件，没有 `_meta` 记录，脚本不敢猜，暂时留着了。真要归位，得从导出内容里反查账号特征，属于脏活。
3. **`pack` 的写点没切到账号目录**（`server/onebot.py`、`server/reader.py`）。
4. **`/api/framework/status` 约 1.1 秒**，加个短缓存就能解决。
5. **多账号同时在线不支持。** QQ 的登录态本质是"当前登录的那一个号"，NapCat 也不例外。所以同步动态、发消息这些只能对当前登录的号做；界面在选择别的号时会明确禁用并提示，不会偷偷借用另一个号的凭据。要真做到"每个号各自一份登录态"，得上多个框架实例，那是另一个量级的改造。
6. **截图不能进仓库。** `docs/截图/` 下那批图里有真实好友昵称和聊天内容，已经加进 `.gitignore`。想公开的话得先打码。
7. **`docs/SPEC-重构接口.md` 的旧章节还没回写。** 新加的接口都补在第 11 章了，前面几章的描述有几处跟实现对不上，我在第 11 章末尾列了冲突清单，但没动旧章节。
