# QQScope 项目说明

写于 2026-10-01。这份文档给两类人看：一是想了解这个项目到底在做什么的人，二是后面要继续改它的人。前半部分讲项目本身，后半部分讲已经踩过和正在踩的坑。

---

# 第一部分：这个项目在做什么

## 1.1 一句话和一个底线

**QQScope 是一个把自己 QQ 聊天记录读出来、在本地做统计和情绪分析的工具，用途是自我观察。**

它不是医疗产品或心理测评。所有对外文案里都写着一句固定的话：辅助自我观察，非医疗诊断。这句话不是走过场——它决定了这个项目能说什么、不能说什么。它能告诉你"最近 30 天你在凌晨 1 点后发过 240 条消息、负面词占比比上月高了 8 个百分点"，但它不会、也不该给你下任何结论。

还有一条底线：**数据全在本机，不出本机**。整个项目里唯一会联网的地方是"AI 解读"，而那个功能在把内容发出去之前，必须先把要发送的原文摆在界面上让人看一眼、确认了才发。

## 1.2 为什么要做这个

起因挺朴素的：我想知道自己这半年到底在什么时候话最多、在跟谁聊、是不是又在熬夜。

市面上没有现成的工具能回答这个问题。QQ 自己的聊天记录翻起来基本没戏——只能一条条滚，没有统计，没有情绪维度，也没法导出成一个能长期保存的东西。而聊天记录恰恰是最真实的样本：一个人半夜两点在群里打字的速度、用词的变化、跟不同人说话的语气差异，这些东西平时自己根本注意不到，攒了几个月回头一看才明显。

所以这个项目的目标从一开始就不是"一次性的好奇心"。它是**长期留档 + 定期回看**：数据持续攒着，想看的时候能拉出一条时间线来。

## 1.3 数据是怎么进来的（两条通道）

项目里把数据来源叫"两个读取窗口"。这个设计是整个项目的主干，值得讲细一点。

### 窗口 A：本机数据库，离线，负责存量

电脑上 QQ 自己的聊天记录存在 `nt_msg.db` 里，位置大概在 `文档\Tencent Files\<QQ号>\nt_qq\nt_db\`。这个库是 NTQQ 时代的产物，用 SQLCipher 加密，而且文件开头还多出 1024 字节的自定义头。

读取流程是这样一条链：

```
nt_msg.db（加密）
   ↓ 剥离 1024 字节头
   ↓ SQLCipher 解密（需要按账号区分的密钥）
nt_msg_plain.db（明文库）
   ↓ 解析 protobuf 消息体
   ↓ 按字段还原出 时间/方向/对端/文本/媒体
统一主库
```

这里有两个地方特别容易翻车，都是实战踩出来的：

**密钥是按账号走的，而且跟着 QQ 版本变。** 一开始我以为密钥就是某个固定值，实际上主号和小号各有一把，QQ 大版本一升级原来的 key 就全废。后来在项目里留了个查找顺序：接口传参 → `data/keys/<QQ>.key` → `data/keys/legacy.key`，密钥失效时用社区脚本（QQBackup 的 `windows_ntqq_get_key.ps1`）重新提取，写进对应文件就行。这个东西没法自动化，是目前唯一需要人工介入的环节。

**方向字段不能只信一个值。** 消息表里有个 `40013` 字段表示方向，但它的取值有 0/1/2/3/4/5 六种，语义不完全对称。最后改成用"发送者 QQ 是否等于本账号"来判断，比只看 `40013 == 1` 准得多。

联系人昵称和群名是另一摊事。它们在 `profile_info.db`、`group_info.db` 里，密钥跟主库不是同一把，早期一直搞不定。现状是：从本地库能拿到多少算多少，拿不到的走窗口 B 的接口去补。

### 窗口 B：机器人框架，在线，负责增量

第二条通道用 NapCat 的 Windows 无头一键版（v4.18.28）。这个选择本身是有讲究的。

NapCat 有好几种发行版，"Shell 注入版"需要挂在本机正在用的 QQ 上，"Framework 插件版"要先装 LiteLoader——这两种都会动到我平时用的那个 QQ，而这是我不能接受的。所以选的是**自带 QQ 内核的 Windows Node 一键版**：它有自己独立的一套 QQ 和 Node，绿色运行，不启动、不关闭、不注入我本机那个 QQ。

登录方式就是扫码（必须本人扫，工具不做代替登录）。登录之后它会监听一个 OneBot HTTP 端口（默认 3000），项目通过这个接口拉好友列表、群列表、历史消息，另外还挂了一个**实时采集线程**，把新到的消息持续灌进库，不用重启框架。

实时采集的节奏是分档的：当前正在看的会话 5 秒轮一次，会话列表前 20 个 30 秒轮一次，其余 10 分钟轮一次。这样既能及时看到新消息，又不会把接口刷爆。

有一件事需要提前说明白：**QQ 的登录态本质上就是"当前登录的那一个号"**，NapCat 也不例外。所以"在线拉取"和"发消息"这两个功能天然只能对当前登录的号生效。项目里的做法是显式化——当你在界面上选了另一个号时，这些按钮会禁用并给出提示，而不是偷偷借用当前登录号的凭据。要真正做到每个号各自一份登录态，需要同时跑多个框架实例，那是另一个量级的改造，目前没做。

## 1.4 数据存在哪、怎么组织

早期是"一个库装所有账号"，后来改成了按账号物理分开：

```
data/
  accounts/
    1605289411/
      qqscope.db          这个号的主库（联系人/消息/动态）
      media_cache/        这个号的图片、语音缓存
      avatars/            这个号看到的头像
      export/             这个号的导出产物
      decrypt/  pack/     解密、解析过程中的中间文件
    1438830763/
      qqscope.db
      ...
  accounts.db             账号注册表（有哪些号、各自多少条）
  server/settings.json    全局配置（端口、AI、发送策略等）
  framework/              OneBot 配置和框架日志
```

库里的核心是三张表：`contacts`（会话/联系人，联合主键是 账号+类型+对端）、`messages`（消息，`direction=1` 表示自己发的）、`feeds`（QQ 动态）。所有表都带 `account_qq` 字段，并且**每一层的查询、接口、前端存储都强制带账号**——缺账号的请求一律拒绝，绝不"兜底成当前登录的那个号"，这是踩过坑之后定下的规矩。

## 1.5 界面上能干什么

不需要懂代码，跑起来看就行。除了数据源页需要配置，其他页面打开就有东西。

**总览**是默认首页。上面一行 KPI（总消息数、自己发的、会话数、时间跨度、活跃天数），下面是情绪曲线和活跃时段两张图，再下面是最近几天的趋势、媒体命中率、语音转写进度。样本少的日子会标一句"该日样本少，仅供参考"——因为只发三条消息的那天算出来的情绪曲线没有意义。

**会话**页左边是会话列表（能搜索、按私聊/群聊分组），右边是消息气泡。图片能点开看大图，语音能直接播，文件、名片、表情都有对应的卡片样式。底部有个输入框，可以在这个页面直接给对方发文本消息——但要过二次确认，群聊会额外提示"N 人会看到"。这是唯一会往外发东西的功能，所以做得很保守。

**导出**页可以勾选任意多个会话，选格式（HTML / TXT / MD）和模式（每人一个文件 / 合并），还能限定时间段（全部 / 最近 7 天 / 最近 30 天 / 自定义），支持全选私聊、全选群聊，最后打包成 zip。导出的 HTML 是自包含单文件，双击就能看，里面带聊天气泡和"仅看自己发的"筛选。

**动态**页是 QQ 空间的说说，能看自己和好友的动态（点赞、评论、转发数）。

**数据源**页是给这两个窗口用的：窗口 A 那边扫描本机有哪些账号、导入，带进度；窗口 B 那边填地址和 token、测试连接、拉取。默认是折叠成两行摘要的，不看细节不会碍事。

**AI 解读**页会把选定的数据整理成一段上下文，交给 DeepSeek 做解读。这一步之前有预览，能先看到要发出去的内容是什么。

**设置**页有数据根目录、AI 配置、端口、发送策略、还有 3D 背景的开关。

**框架终端**是嵌在页面里的 NapCat 控制台，能直接看到框架自己的输出（登录、收发消息、报错），不用切窗口。

## 1.6 情绪分析是怎么算的

这部分在 `app/js/analysis.js` 里，是纯 JavaScript，不依赖任何外部库，词库只有这一份真源。

统计口径上有个基本决定：**只分析自己发出的消息**（`direction=1`）。因为要观察的是"我"的状态，不是聊天的氛围。

打分逻辑经过一次重写，现在包含几块：情绪词典（正/负词）、否定词和程度副词的处理（"不太开心"不能算开心，"非常烦"要加权）、emoji、深夜时段权重，以及一些行为信号（回复节奏、发言集中度）。最后加权聚合成按天的情绪值和波动幅度。

除了情绪曲线，它还会输出：活跃时段分布、按消息数排序的社交对象、自己发的高频词。这几个指标在样本量小的时候都不稳定，所以界面上会同步显示"覆盖率"（有信号的消息占比），低于一定比例就提示样本不足。

## 1.7 技术栈和目录

| 部分 | 用了什么 |
| --- | --- |
| 后端 | Python 3.14 + FastAPI + uvicorn，端口 15555 |
| 数据库 | SQLite（每账号一个库） |
| 前端 | 原生 JS 单文件（源码 `web/index.html`，构建产物 `app/dist/QQScope.html`），零外部请求 |
| 解密解析 | QQBackup 的 `nt_msg_db_util` 工具链 + sqlcipher3 + protobuf |
| 在线通道 | NapCat（OneBot HTTP 3000 / WebUI 6099） |
| 语音转文字 | faster-whisper（本地跑，一次性离线任务） |
| 3D 背景 | three.js + GLTFLoader + 一个 VRM 模型 |
| AI 解读 | DeepSeek API（可选，默认不填 key 就是不启用） |

目录大致是：`core/` 数据层（`store.py` 主库、`paths.py` 路径、`export.py` 导出、`media.py`/`voice.py` 媒体与语音、`sources/` 两个窗口），`server/` 是 FastAPI（`app.py` 加一堆 `routes_*.py`，路由模块是自动挂载的），`web/` 是前端源码和自测脚手架，`scripts/` 是构建、打包、验收脚本，`tools/` 放第三方工具链（不改），`data/` 是运行数据。

## 1.8 怎么跑起来

最省事的是便携包：解压之后双击「①启动QQScope.bat」，它会自动构建前端、起后端、打开浏览器。要用在线通道再双击「②启动机器人框架.bat」扫码。

从源码跑就是一条命令：`tools\nt_msg_db_util\.venv\Scripts\python.exe server\app.py`，然后浏览器开 `http://127.0.0.1:15555`。

验收有两条：`scripts\verify.py --full` 是后端的端到端（含真实数据导入导出），`web\selftest\run_edge.ps1` 是前端的一键验收（自建 mock 后端 + 无头 Edge）。

# 第二部分：遇到的问题

下面这些是 2026-10-01 这一天里集中暴露出来的。我按类别整理，每一类都写清楚现象、根因、怎么处理的、以及留下了什么。

## 2.1 前后端通信

**现象**：网页用起来一直不利索，请求偶尔要等很久。

**排查过程**：第一反应是代理。这台机器上挂着 `127.0.0.1:7890` 的系统代理，之前本地请求被它劫持过（Python 那边得加 `trust_env=False`）。但查注册表，绕过列表里本来就有 `localhost` 和 `127.*`，代理不背锅。

实测之后原因很清楚：

```
http://127.0.0.1:15555   -> 200 (202 ms)
http://localhost:15555   -> 200 (2090 ms)   ← 慢了一个数量级
http://[::1]:15555       -> 连接被拒绝
```

后端一直绑的是 `0.0.0.0`，也就是只有 IPv4。浏览器打开 `localhost` 时会先试 IPv6 的 `::1`，被拒之后才回退到 IPv4，**每次请求白白等两秒**。页面上的轮询是密着的（登录门 3 秒一次，还有实时采集、框架日志），两秒的回退乘上去，用起来就是"通信有问题"。

**处理**：修的过程里我自己先踩了一个坑——想当然把监听改成 `host="::"`，结果这台机器上它变成 v6-only，反倒把 `127.0.0.1` 彻底断了。最后改成 IPv4 主服务不动、额外用守护线程挂一个 `::1` 回环监听：

```
127.0.0.1 -> 177 ms（冷启动）
localhost ->  55 ms   （原来 2090 ms）
[::1]     ->  43 ms   （原来直接拒绝）
```

**同类旧账**（之前踩过、已修）：验收脚本 `verify.py` 明明 9/9 全绿却退出码是 1，原因是最后那行带 emoji 的输出在 GBK 控制台抛编码异常；`build_web.py` 直接往 stdout 打中文，被当子进程读的时候会乱码。

**还留着的**：`/api/framework/status` 每次约 1.1 秒，它要查 WMI 进程列表和 netstat。只在框架终端页用到，加个两秒缓存就能解决，暂时没动。

## 2.2 文件存储

**现象**：所有账号的数据挤在一块儿。一个 `data/qqscope.db` 装着所有 QQ 的联系人、消息、动态，`media_cache`、`avatars`、`export` 也都是全局唯一一份。

查询逻辑上早就按账号过滤了，前端也是分开的，但物理上就是混着的。这既不符合"每个号自己一个文件夹"的要求，也让人不放心——谁能保证哪天某个查询漏了 `account_qq` 呢。

**处理**：改成按账号物理分开，库和文件都进去（结构见 1.4）。`store.connect()` 现在接受账号参数，传账号就打开那个号的库，不传就是注册表；删账号从"删一堆行"变成"删整个目录"。

真实库已经迁完，拆出两个账号目录（主号 283,048 条 / 第二个号 8 条）。迁移前备份在 `data/backup/legacy_split_20261001_224741.db`，**老的单库没删**，改名成 `data/qqscope.db.migrated` 留着。文件那一层也做了迁移，备份在 `data/backup/files_split_20261001_225944/`。

**遗留**：迁移脚本的原则是**判不出归属的一律不删也不乱移**，所以现在还有一批留在原地：老的导出目录里 52 个没有 `_meta` 记录的旧任务（合计 17708 个文件，是最大的一坨）、212 个头像、28 个媒体缓存、26 个解密中间文件、2 个 pack 文件。这些都是历史产物，不影响新数据。另外 `pack` 的写盘点在 `server/onebot.py` 和 `server/reader.py` 里，这次没在改动范围内。

## 2.3 网页端的预览

"预览"在项目里指好几个地方，分开说。

**AI 解读的预览**之前是彻底坏的：页面上一直显示「等待数据加载…」。原因说出来挺蠢——调用 `ensureReport()` 的地方从第四个版本就在，但函数的定义在某次改版里被删掉了，页面直接抛 `ensureReport is not defined`，后面的渲染全断。修完实测：AI 页 `data-js-errors=0`，预览里有真实内容。这个预览本身有意义，因为按约定，要调 AI 之前得先把将发出去的内容摆出来看一眼。

**媒体预览**包括图片灯箱、语音气泡、文件卡片、名片卡和表情。这里的老大难是群聊里的历史图片——QQ 客户端自己清了缓存，本地没有原文件，命中率一直上不去。解决办法是用 NapCat 的登录态回头去拉（`nc_get_rkey` 加包里的 fileid 拼直链），界面上有补下载入口，限速 0.6 秒一条、可以中断。语音那边走过一段弯路：本地 ASR 一开始慢得离谱（35 分钟只跑完 198 条），后来发现是线程超订（10 个 worker 每个开 8 线程去挤 20 核），改成多进程少线程才正常，现在待处理已经清到 0。

**导出页的预览**指的是时间段筛选和分组：能选全部 / 最近 7 天 / 最近 30 天 / 自定义起止，会话列表按私聊在前、群聊在后分组。

这里要坦白一句：我一开始并不确定对方说的"预览"具体指哪一处。上面三块是代码里所有叫预览的地方，按核对过的状态都写了。如果指的是别的现象（比如消息列表滚动的懒加载、资料卡弹出、或者导出 HTML 打开后的样子），那还得再看一次，这次先把已知的落下来，不猜。

## 2.4 3D 旋转背景

背景这个需求是从"界面太素了，跑个模型环绕一下"来的。做法是本地 three.js 加 GLTFLoader 加载一个 VRM 模型（43 MB），在登录页和主界面上做环绕动画。素材走本地文件，静态 HTML 里不写 `<script src>`，都是运行时按需注入，打不开就退化成一层 CSS 光晕。

查出来一个挺典型的 bug：**后端从来没挂载过 `/assets`**。也就是说这个 3D 背景在真实产品里一直没生效——请求 `/assets/vendor/kei.vrm` 直接 404，前端静默降级成 CSS 光晕，界面上看不出错，只是模型不出来。

一直没发现的原因值得记一笔：v10 的验收用的是测试脚手架 `web/selftest/v10_server.mjs`，那个脚本自己实现了 `/assets` 的转发，所以**自测全绿、真机不生效**。教训是，素材类的断言必须在真后端上再跑一遍，不能只信自建的 mock 服务。

补上挂载之后实测 `200 / 44,845,856 B`，模型能正常加载。围绕这个文件还有几件事：它**不进 git**（43 MB 纯二进制），换机器要跑 `scripts/fetch_assets.ps1` 从参考项目复制；便携包和 exe 里是打进去的，所以那个 exe 有 145 MB，其中很大一块就是这个模型；无头浏览器（软渲染）里帧率很低，代码里做了自适应，帧率连续低于 24 就自动关掉 3D，属于设计内的降级。

## 2.5 其他一并修掉的

这几条不在上面四类里，但都是同一天暴露的真问题，顺手记一下。

**退出登录退不出去。** 点「退出登录」默认只走温和路径（给框架发一个退出指令），框架不理它的时候就只弹一条横幅，实际上还登录着；而界面又会按框架的登录号自动重进主界面，所以给人感觉"退不出去"。现在改成一次到位：先试温和退出，2.4 秒没断就直接结束框架进程（结束前仍然要校验那个 PID 确实是 node.exe 且命令行含 napcat，不会误杀别的进程）。同时补了一个「全部退出」，一次动作把停采集、退框架、清登录标记、回连接门都做掉。

**登录二维码过期了刷新不了。** NapCat 只在启动时写一次二维码文件，过期后它自己不会重写；而原来的「刷新二维码」只是把同一个文件重新显示一遍，等于没用。现在后端会带上二维码的年龄，界面上直接标"已过期（已 N 秒）"，刷新按钮改成重启框架拿一张新码。

**实时采集到的账号看不见。** 这个是自己发现的：框架登录一个新号之后，实时采集确实在按登录号入库，但没人给这个号在注册表里建行，于是消息成了孤儿——数据在库里，接口列不出这个账号，界面上就永远看不到。修完之后实测孤儿从 8 条变成 0，并且把"无孤儿账号行"做成了常驻验收项。

**名片消息显示不对。** 界面上有一万多条消息显示成光秃秃的 `[名片]`。查下来不是缺昵称那么简单，是分类函数把"戳一戳""群提醒"这些也当成名片了。重新按字段判据分开之后，光秃名片从 12367 条降到 833 条，多出来的是 9970 条戳一戳和 320 条群提醒。

**语音一直转不完。** 除了上面说的线程超订，还有一个过滤条件写错，导致"本地缺文件"的那条永远不被标记，待处理数永远清不到 0。
